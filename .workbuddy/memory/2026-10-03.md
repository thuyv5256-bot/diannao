## B.2 迁移「今天生意怎么样」页（UI v2）

**改动范围**：仅该页 + 新增 `core/feedback_view.py`、`tests/test_feedback_view.py`；
`app.py` 只改了 import / CSS 拼接 / Tab3 布局 / load_feedback_template / submit_feedback /
submit_feedback_full 及其绑定。其他页面未动。

### 修改前确认的 5 个业务事实（有据可查，勿再重复分析）

1. **日期语义**：`fb_date` 默认 `LAST_DAY=2026-08-27`，是 CSV 180 天经营数据的最后一天，
   语义为「已经卖完货的那一天」，不是当天。首页 `DEFAULT_PLAN_DATE=2026-08-28` 是次日备货日，
   两者相差一天 → 所以文案不能写「今天」。
2. **换日期不刷新**：`load_feedback_template()` 原本无参数、硬编码 `LAST_DAY`，且只绑
   `btn_tpl.click(..., None, fb_df)`，`fb_date` 没有任何 change 绑定。
   现改为接收 day 参数并由按钮传入（只改数据源指向，阈值与口径未动）。
3. **数据来源**：`memory.get_sales_range(sku, day, day)` 读 `sales` 表（SQLite）。
   **实测 9000 行中 `qty_stockout` 与 `qty_spoilage` 全为 0** → 只有「实际卖出」有历史值，
   断货/损耗两列必须店主自己填。页面已如实说明，未宣称 POS 自动采集。
4. **保存是否进入学习**：是。`submit_feedback` → `evolution.process_feedback(persist=True)`
   → 写 `feedback_log` / `experiences` / `evolution_log`（阈值 STOCKOUT_TRIGGER=SPOILAGE_TRIGGER=0.1）。
5. 载入 50 行（row_count 16 fixed 意味着界面上只显示前 16 行，与历史行为一致，未改）。

### 关键实现约束（后续页面沿用）
- 保存反馈**必须**按 `result["changes"]` 是否为空决定文案：
  空 → 只说「已保存 / 没有触发新的策略调整」；非空 → 才展示经验明细表。不得伪造 Memory 命中。
- 四个真实分支：changes（真实校准）/ skipped（幂等去重）/ updated（数据修正）/ removed（异常消除撤销）。
  注意 updated 场景下 changes 往往**非空**（会真的重算校准），此时走 changes 分支才是正确的。
- 列名口径：商品 / 实际卖出 / 没买到（断货）/ 损耗（报废）/ 商品编号，
  sku 取自「商品编号」列；`FB_COLUMNS` 与 `submit_feedback` 取值必须同源（定义在 feedback_view）。
- 保存按钮独占一行做主 CTA，「载入实际数据」降为 secondary 次级操作。

## B.3 迁移「它学会了什么」页（UI v2）

**改动范围**：重写 `core/learn_view.py`（v2 表达）；`app.py` 改了 Learn Tab 头（用
`learn_view.render_head()` 替掉两行 gr.Markdown）、`render_evolution_html` 与

其他页面未动。

### 修改前确认的 5 个业务事实
1. **demo-store 真实学习记录**：`experiences=0`、`evolution_log=0`、`feedback_log=301`。
   本页只读 `experiences`/`evolution_log` → 当前如实显示「还没有形成经营经验」空状态。
   feedback_log 的 301 行未沉淀为经验（未超阈值），不进入本页。
2. **数据来源**：`memory.get_experiences()`（experiences 表）+ `memory.get_evolution_log()`
   （evolution_log 表）。与 FINAL/FROZEN 实验数据（eval/ 下 739 经验/6366 命中/2832 决策改变）
   **完全分离**——本页不 import 也不读 eval，FINAL 数据不会混入 demo-store 页面。
3. **经验形成条件**：经营反馈中 断货占比 > STOCKOUT_TRIGGER(0.1) 或 报损占比 >
   SPOILAGE_TRIGGER(0.1) 才由 `evolution.derive_experiences` 沉淀为经验；日常小波动不触发（防噪声）。
4. **当前是否发生策略变化**：否（evolution_log=0）。只有校准量真变时才写 evolution_log。
5. **可追踪性**：schema 支持 反馈(feedback_log day+sku) → 经验(experiences day+sku) →
   后续变化(evolution_log day+sku) 闭环；本页按 (day,sku) 关联展示，但当前无数据。

### 关键实现约束
- 经验卡 `lx-exp` 三行：发生了什么 → 小满记住了什么(lesson) → 以后会怎样参考(adjustment)；
  仅当 evolution_log 有同 (day,sku) 才补「已影响后续补货 + 安全库存系数变化」，否则说「只记下来、没触发调整」。
- 页面底「它是怎么学的」流程线（经营结果→记进老账本→总结经验→影响以后补货）用 `.lx-flow` 轻量行，无四张卡/动画/emoji。
- **严禁**：未改 evolution/memory/阈值/参数/schema/forecast/R³/FINAL；未写库（无污染）；未跑正式实验。

### 测试
