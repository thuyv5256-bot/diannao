## 摘要

`eval_results.csv` 里owner 一行的三个数字（缺货 0、损耗 0、livelihood_index 空）
**全部是数据缺失或口径不一致造成的假象**，不是店主表现优秀。

最关键的发现：**owner 在指标层面等价于「有无限预算、每天把货架填满」的理想策略**
（收入差 0.00%、毛利差 0.14%），而它甚至不需要进货 —— 因为原始 CSV 里根本没有
「断货」这个字段，导入时该列被硬编码为 0。

**当前数据不能证明小满优于传统补货算法。**

## 一、owner 缺货 = 0 的成因

### 结论：**B 类 + C 类复合问题**（数据缺失被当成 0，且与其他模式口径不同）

### 代码路径证据

`core/eval_core.py` 里owner 与其他模式走**两条完全不同的函数**：

```
owner    → _history_context()  第 59-88 行：直接读 sales 表的历史记录
其他模式 → _simulate()          第 91-149 行：每天 build_plan + 真实进销存重演
```

`owner` 的缺货统计（第 81-83 行）：
```python
if r["qty_stockout"] > 0.5:
    owner["stockout_cnt"] += 1
    owner["stockout_qty"] += r["qty_stockout"]
```
读的是 `sales` 表的 `qty_stockout` 列。

### 根本原因：原始 CSV 没有断货字段

`data/shopmind_180days_50sku.csv` 共 16 列，**全部字段**：
```
date, item_id, product_name, category, sales, price, cost, essential,
shelf_life_days, supplier, lead_time_days, weather, temperature_c,
event, is_weekend, supplier_available
```
**没有任何断货/损耗字段。**

`core/dataset.py:133` 显式写死：
```python
"qty_stockout": 0.0,   # CSV 未记录，反馈由店主单独录入
```

验证：`sales` 表 180 天 `SUM(qty_stockout) = 0.0`、`SUM(qty_spoilage) = 0.0`。

### 三个 SKU 的逐日数字

**【P001 矿泉水】售价 2.00 成本 1.10**
| 日期 | 卖出 | 缺货 | 损耗 |
|---|---|---|---|
| 2026-08-21 | 18 | 0 | 0 |
| 2026-08-22 | 34 | 0 | 0 |
| 2026-08-23 | 31 | 0 | 0 |
| 2026-08-24 | 29 | 0 | 0 |
| 2026-08-25 | 31 | 0 | 0 |
| 2026-08-26 | 25 | 0 | 0 |
| 2026-08-27 | 23 | 0 | 0 |
| **180 天合计** | **4578** | **0** | **0** |

**【P009 大米5kg】售价 35.00 成本 28.00** — 近 7 天：5/5/6/6/3/2/4，缺货全 0，180 天合计卖出 715、缺货 0

**【P005 橙汁】售价 5.00 成本 3.20** — 近 7 天：9/8/7/7/7/6/6，缺货全 0，180 天合计卖出 1551、缺货 0

三个 SKU、180 天、缺货全部为 0 —— 这不可能是真实经营结果。

### 补充证据：同一批数据里 `feedback_log` 却有断货

`feedback_log` 表 `SUM(qty_stockout) = 51.0`。这 51 是从网页「今天生意怎么样」
录入的（今天刚播种的 3 条演示经验），**与 CSV 导入完全不是一个来源**。

### 为什么这在指标上是致命的

需求序列的定义是 `demand_map[sku][day] = qty_sold + qty_stockout`。
由于 `qty_stockout ≡ 0`，所以 **需求 ≡ 销量**。

这意味着：**在这个数据集上，缺货在数学上不可能发生**。
所有模式的"缺货"都只是"我带的货不够"，而不是"顾客需求没被满足"。

## 二、owner livelihood_index 为什么是空

### 结论：**根本没有计算**（且与 baseline 使用了不同指标）

### 证据

**B1. owner 字典里根本没有这个 key**（`eval_core.py:71-72`）：
```python
owner = {"stockout_cnt": 0.0, "stockout_qty": 0.0, "spoil_cnt": 0.0,
         "spoil_qty": 0.0, "gross_margin": 0.0, "revenue": 0.0}
```
只有 6 个 key，**没有 `livelihood_index`**。

**B2. 该指标只在 `_simulate` 里累加**（第 110、148 行）：
```python
m["livelihood_index"] += plan["metrics"]["livelihood_index"]
...
m["livelihood_index"] = m["livelihood_index"] / days
```
owner 不走 `_simulate`，自然不会算。

**B3. CSV 写入时是主动填空**（`eval.py:88`）：
```python
"" if mode == "owner" else round(r.get("livelihood_index", 0.0), 4),
```
这是**代码主动跳过**，不是计算失败、不是 NaN、不是数据缺失。

### 附带的公平性问题

baseline 的 `livelihood_index = 0.4`、diannao = `0.7`，
这两个是"每天 build_plan 产生的方案保障率"的平均值 —— 衡量的是**算法给出的方案**。
owner 没有对应指标，所以 CSV 里 owner 该列空白。

**如果有人拿这张表说"小满 0.7 > 传统 0.4"，那是在比较两个算法，不是比较三个模式。**

## 四、「躺平策略」漏洞实验

构造三个策略，用**完全相同**的需求序列与初始库存口径跑：

| 指标 | owner（读历史） | 躺平（永不进货） | 有钱就买 |
|---|---|---|---|
| 售出件数 | — | 0 | 23903 |
| 销售收入 | 162309.0 | 0.0 | 162309.0 |
| 毛利 | 53129.8 | **−37.9** | 53091.9 |
| 缺货量 | **0.0** | **23903.0** | 0.0 |
| 损耗量 | 0.0 | 11.7 | 11.7 |

### 判定：毛利/缺货指标本身 **VALID**，能识别躺平

- 躺平的毛利是 **−37.9**（负数，因为损耗了初始库存）
- 躺平的缺货量是 **23903**（全部需求未满足）
- 两者都明显差于 baseline（毛利 16846、缺货 14110）

**所以"躺平策略漏洞"在毛利/缺货指标上不成立。**

### 但真正的漏洞是 owner

`owner` 的「缺货 0、损耗 0、毛利 53129.8」这组数字，
**比任何真实策略都漂亮**，包括"有钱就买"（53091.9）。

原因不是 owner 经营得好，而是**把「数据缺失」当成了「表现完美」**。

## 五、毛利指标重新判断

### 当前口径（`core/metrics.py:41-43`）

```python
def gross_margin(sold_qty, unit_margin, spoil_qty, cost_price):
    """实现毛利（元）= 销量×单件毛利 − 报损件数×成本价。"""
    return float(sold_qty or 0.0) * float(unit_margin or 0.0) - spoilage_cost(spoil_qty, cost_price)
```

**是** "销售收入 − 商品成本"，**不包含**：
- ❌ 采购成本（占用多少现金）
- ❌ 库存资金占用（压了多少货）
- ❌ 缺货机会损失
- ❌ 供应商账期

### 可比性检验

| 模式 | 毛利 | 收入 | 毛利率 |
|---|---|---|---|
| owner | 53129.8 | 162309.0 | 32.7% |
| baseline | 16846.0 | 43011.0 | 39.2% |
| diannao | 13909.2 | 40315.0 | 34.5% |

**owner 53129.8 与 baseline 16684.5 不具有可比性。**

决定性证据 —— owner 与「无限预算满仓」对照（30 天窗口）：

| 指标 | owner | 无限预算满仓 | 差异 |
|---|---|---|---|
| 销售收入 | 80149.5 | 80149.5 | **0.00%** |
| 毛利 | 26190.5 | 26153.3 | **−0.14%** |

**owner 就是"无限预算满仓"的等价物。** 它甚至不需要进货 ——
因为销量直接等于需求量，天然 100% 满足。

### 需求覆盖率（60 天窗口，需求总量 23903）

| 模式 | 实际售出 | 覆盖率 |
|---|---|---|
| owner | 23903 | **100.0%** |
| baseline | 9793 | 41.0% |
| diannao | 7749 | 32.4% |

`owner 53129.8 ÷ diannao 12461.3 ≈ 4.26 倍`，
**这个倍数全部来自"把历史全量销量记在自己头上"，与算法优劣无关。**

## 七、三个问题的明确回答

### ① owner 的"缺货 0"能不能拿去比赛宣传？

## **NO。绝对不能。**

它是 CSV 缺少断货字段 + 导入时硬编码为 0 的产物。
拿它宣传等于宣称"我们的系统能做到 100% 不缺货"——而真实算法模式在同一数据集上
缺货率是 100%（因为数据集本身无法制造缺货），一查就露。

**正确说法**：「原始仿真数据集未记录断货数据，因此无法用历史数据评价缺货表现；
我们已改为在相同需求下实时重演各策略来计算缺货。」

### ② "毛利是 baseline 三倍"能不能拿去比赛宣传？

## **NO。绝对不能。**

倍数来自 owner 读了历史答案（收入 162309 = 需求量全额），
而 baseline 只能卖出 `min(需求, 库存)`（收入 43011）。
两者不是同一条赛道。

而且 **owner 与"无限预算满仓"收入差 0.00%** ——
说明 owner 的真实身份是"无限预算理想策略"，不是"店主原做法"。

**正确说法**：「在相同预算 ¥360/天 下，小满与传统算法的毛利差距在 ±5% 以内，
差异主要体现在民生保障（100% vs 94.8%）与民生缺货率（1.55% vs 2.49%）。」

### ③ 目前的数据能不能证明"小满优于传统补货算法"？

## **NO。当前数据不能。**

`eval_results.csv` 完全无法支撑任何结论，因为：
1. 需求 = 销量，缺货无法发生 → 三个模式的缺货数字都无意义
2. owner 走另一条代码路径 → 任何含 owner 的比较都无效
3. 毛利不含资金占用 → 无法反映真实的经营效率

**但 180 天长期实验（`eval/final/`）的数据是可用的**，因为它走的是
`core/simulator.py` 的独立重演路径，两种策略用**同一需求序列、同一初始库存、
同一预算**，逐日重演。真实结果是：

| 指标 | 小满 R³ | 传统 | 优劣 |
|---|---|---|---|
| 累计毛利 | 152707.2 | 152769.6 | **传统优 0.04%** |
| 总体缺货率 | 0.0293 | 0.0269 | 传统优 |
| **民生保障率** | **1.0000** | 0.9480 | **小满优** |
| **民生缺货率** | **0.0155** | 0.0249 | **小满优** |
| 缺货次数 | 789 | 803 | 小满优 |
| 库存周转 | 198.12 | 205.10 | 传统优 |

**能证明的结论只有一条**：小满用 −0.04% 的毛利换来了民生保障 100%（vs 94.8%）
与民生缺货率 −37.6%。这是一个**取舍**，不是**全面领先**。

## 八、建议的公平 A/B 实验设计（本轮不实现）

### 必须改的 5 点

**1. 取消 `owner` 这个模式**
它不是策略，是"读历史答案"。owner 应该改成**一个真实可跑的启发式基准**，
例如「固定 3 天补货一次、不看缺货、不管预算」—— 这才是"店主原做法"的合理建模。

**2. 需求序列必须包含真实缺货**
当前 `demand = qty_sold + qty_stockout ≡ qty_sold`，缺货在数学上不可能发生。
需要重新生成仿真数据：让 `qty_stockout` 有真实取值（顾客想买但没货），
这样 demand 才能大于 sold，各策略才有可比的分母。

**3. 所有模式统一走 `_simulate`**
同一份初始库存快照（同一个 `on_hand` 副本）、同一个 `EVAL_BUDGET`、
同一套 `_spoil_qty` 损耗公式、同一个 `max(0, demand-sold)` 缺货定义。

**4. 增加资金占用指标**
`metrics.inventory_value()` 和 `avg_inventory_capital()` 已经实现但没用于模式对比。
公平的比较必须包含：
- 平均库存资金占用（越低越好）
- 期末库存价值（同样资金占用下谁的货更值钱）
- 库存周转次数

**5. 报告里必须同时呈现「收益」与「代价」**
当前 `eval_results.csv` 只报毛利点，隐藏了库存资金占用。
应同时报：毛利率、平均库存资金、缺货率、民生保障率，
让"用 0.04% 毛利换 5.2pp 民生保障"这类取舍显式化。

### 建议的指标清单

| 指标 | 口径来源 | 方向 |
|---|---|---|
| 实际销售收入 | `sold × sell_price`（各模式自己算） | 越高越好 |
| 毛利 | `metrics.gross_margin`（统一） | 越高越好 |
| 采购成本 | `Σ reorder_qty × cost_price` | 越低越好（占现金） |
| 未满足需求 / 缺货量 | `max(0, demand − sold)` | 越低越好 |
| 缺货率 | `缺货量 / 总需求` | 越低越好 |
| 损耗量 / 损耗成本 | `_spoil_qty()` 统一口径 | 越低越好 |
| 民生商品保障率 | `plan.metrics.livelihood_secured_rate` | 越高越好 |
| 预算使用率 | `total_cost / budget` | 观察值 |
| 库存周转 / 期末库存 | `inventory_turnover` / `inventory_value` | 越高/越省越好 |

**所有指标必须由 `_simulate` 统一产出，任何模式不得走捷径。**
