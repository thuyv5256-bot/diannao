## 1. 背景与问题

**谁**：城市社区里的夫妻小店（无专职店员、无数据分析能力、无 IT 预算）。
**现状**：进货全凭经验与记忆，缺工具支撑。
**后果**（两头吃亏）：

| 痛点 | 表现 | 根因 |
|---|---|---|
| 积压损耗 | 短保/季节性商品进多了，过期报损 | 不知道"该进多少"，靠感觉 |
| 刚需断货 | 米面油盐、饮用水断货，居民白跑一趟，客流流失 | 预算紧张时优先砍低毛利商品 |
| 不会总结 | 同一个错误（某商品每年这个时候都卖不动）反复犯 | 没有沉淀机制，经验留在人脑里 |

**市场空白**：现有进销存 / 智能补货系统几乎都面向大型商超——部署复杂、按年收费、需要 POS 与专业硬件。**小店主用不上、也用不起。**

## 2. 产品定位与目标

**定位**：浏览器打开即用的轻量化智能补货决策 Agent，在追求门店经营收益的同时加入**惠民约束**，兼顾小店抗风险能力与社区居民的便民需求。

**产品目标（按优先级）**

| # | 目标 | 说明 |
|---|---|---|
| G1 | **给出可直接执行的每日进货建议单** | 店主看得懂、照着买即可，含金额、件数、理由 |
| G2 | **民生商品不因预算紧张而被砍断** | 多目标决策，而非单期毛利最大化 |
| G3 | **越用越准：从真实经营结果中学习** | 不需要重训模型，校准可解释的业务参数 |
| G4 | **每个建议都能被追问"为什么"** | 决策依据可追溯、可解释、可反驳 |
| G5 | **零门槛、零成本、纯离线可跑** | 无硬件、无数据分析基础、无网络也能用 |

**非目标（明确不做）**

- ❌ 不做完整 ERP / 进销存 / 收银系统（不替代 POS）
- ❌ 不做大模型微调或端到端生成式决策（决策必须确定性、可解释、可复现）
- ❌ 不做多门店连锁总部管理、不做供应链协同平台
- ❌ 不做真实门店数据采集（本项目为**仿真数据**驱动）
- ❌ 不做移动 App（浏览器网页即可）

## 3. 用户与角色

| 角色 | 谁会用它 | 核心诉求 | 对应页面 |
|---|---|---|---|
| **店主（主用户）** | 社区小店经营者 | 明天进什么、进多少、花多少钱；今天卖得怎么样要能记一笔 | 今天该进什么货 / 今天生意怎么样 / 为什么这样进 |

| **开发者/接手人** | 后续维护者与 Agent | 无门槛接手、知道进度和下一步 | [../AGENT.md](../AGENT.md) / [ARD](ARD.md) / [TRD](TRD.md) |

## 4. 核心使用场景

**S1｜每晚备货（最高频）**：店主打开「今天该进什么货」→ 看到一屏建议单（金额/件数/风险提示）→ 可勾选"明天高温/暴雨/节假日/供应商断货"重算 → 照着下单。

**S2｜次日记账与学习**：店主在「今天生意怎么样」录入昨日**实际卖出 / 没买到（断货）/ 损耗（报废）**→ 保存 → 系统按阈值判定是否形成经营经验、是否调整策略参数 → 「它学会了什么」展示"学到了什么、以后怎么变"。

**S3｜追问依据**：店主对某个商品点开「为什么这样进」→ 看到目标库存怎么来、覆盖天数怎么算、有没有历史经验参与、R³ 怎么取舍。

**S4｜异常日**：高温/暴雨/节假日/供应商断供。系统先查历史证据（够不够、稳不稳），**证据强才改预测**，证据弱只给风险提示，不瞎调。

**S5｜评审看证据**：评委打开「实验验证」看到 180 天长期实验的冻结结论（小满 vs 传统纯利润、Memory 开/关、三目标消融），或运行 `python eval.py` / `python run_digital_store.py` 自行复现。

**S6｜自然语言提问**（增强）：在首页输入"预算600元，明天高温"，Agent 读历史 → 找事件 → 分析影响 → 出方案并解释。

## 5. 功能需求（FR）

> 状态口径：**已完成** = 代码已实现且有测试/实验证据；**部分** = 主流程可用但仍有缺口（缺口见 ARD）；**待办** = 尚未实现。

### FR-01 今日补货建议单（首页）
- 描述：一屏给出"今天/明天该进什么货"，含商品名、建议进货件数、预计花费、风险提示；提供预算与日期输入、风险事件勾选（暴雨/高温/节假日/供应商断货），勾选即重算。
- 验收标准：
  1. 打开页面无需任何输入即出方案（默认 `DEFAULT_PLAN_DATE=2026-08-28`、预算 ¥600）；
  2. 每个商品行可回答"进多少 / 为什么"，无写死数字；
  3. 民生商品有明确标记；
  4. 预算不足时如实提示"预算受限"而非静默少进。
- 状态：**部分**（功能已在；页面仍用旧视觉体系 + emoji，v2 迁移未做）

### FR-02 决策依据页（为什么这样进）
- 描述：按商品展示结论 + 证据链：目标库存构成、覆盖天数来源、安全库存来源、历史经验是否参与、R³ 取舍结果。
- 验收标准：任一数字都能在页面上找到"它是怎么算出来的"；不暴露内部推理细节给学生看，只讲业务因果。
- 状态：**部分**（`why_view.py` 逻辑完整、视觉为旧体系）

### FR-03 经营反馈录入
- 描述：按日期录入每个商品的**实际卖出 / 没买到 / 损耗**；保存后触发策略学习；支持"载入实际数据"作为初值。
- 验收标准：
  1. 列名与取值同源（`feedback_view.FB_COLUMNS`），sku 取自"商品编号"列；
  2. 保存后按真实分支给文案：有校准 → 展示经验明细；无校准 → 只说"已保存，未触发调整"；重复提交 → 幂等不重复学习；
  3. 无历史断货/损耗数据时如实说明需店主自己填（CSV 不含这两项）。
- 状态：**已完成**（`core/feedback_view.py` + 10 项测试）

### FR-04 学习成果页（它学会了什么）
- 描述：展示已沉淀的经营经验与策略参数变化轨迹（含单商品参数演进曲线）。
- 验收标准：
  1. 数据只来自本店记忆库（`experiences` / `evolution_log`），**不得混入实验数据**；
  2. 无经验时显示真实空状态；
  3. 每条经验讲清"发生了什么 → 记住了什么 → 以后怎么参考"；只有真正触发变化才说"已影响后续补货"。
- 状态：**已完成**（UI v2 已迁移；当前 demo-store 数据下为真实空状态）

### FR-05 经营档案页（店里的老账本）
- 描述：门店长期记忆的可视化：经营记录规模、历史事件（高温/暴雨/节假日/断供）、商品档案、供应与到货、经营经验。
- 验收标准：数字全部来自 `memory.memory_stats()` / `get_events_summary()` / `analysis.sku_health_report()` / `get_suppliers()`；空数据如实显示空状态。
- 状态：**已完成**（UI v2 已迁移）

### FR-06 实验验证页
- 描述：展示 180 天 Digital Store 长期实验的冻结结论（主对比 + Memory A/B + 三目标消融）。
- 验收标准：
  1. 只读 `eval/final/final_experiment_summary.json`，不重跑、不写死数字；
  2. 结论必须说明差异归因（是"决策目标"还是"有没有记忆"造成的）；
  3. 提供可复现命令。
- 状态：**部分**（数据链路完整；视觉未过 v2；存在待解释的异常项，见 ARD T-EXP-02/03）

### FR-07 项目说明页
- 描述：回答"解决什么问题 / 怎么解决 / 技术实现"；附一键离线评测柱状图（隔离临时库，不动线上记忆）。
- 验收标准：无 Key、无命令行也能看到证据图。
- 状态：**部分**（功能在；视觉未过 v2；内嵌评测需 gradio/plotly 环境）

### FR-08 Agent 工具链与决策追踪
- 描述：把一次决策拆成六个可验证的工具步骤（Inventory / Event / Memory / Forecast / Supplier / R³ Optimizer），每步数据来自真实执行，失败如实显示。
- 验收标准：任一工具失败不得静默跳过；不伪造 Tool Calling。
- 状态：**已完成**（`core/decision_trace.py`，`tests/test_event_tool.py` 覆盖）

### FR-09 LLM 人话解释层（可选）
- 描述：把方案翻译成店主能懂的话，支持追问。
- 验收标准：未配置 `DEEPSEEK_API_KEY` 时自动降级为规则模板，**功能与决策完全不受影响**；LLM 不参与任何数值决策；用标准库 `urllib` 调用 OpenAI 兼容接口（不新增依赖）。
- 状态：**已完成**（`core/llm.py`）

### FR-10 长期记忆库与数据导入
- 描述：SQLite 持久化商品/策略/销量/库存/事件/经验/反馈/进化/计划九类数据；从 CSV 一键导入并可重置。
- 验收标准：重复导入幂等（uid 唯一索引）；清空重建可复现（`python seed_data.py`）。
- 状态：**已完成**（`core/memory.py` / `core/dataset.py`）

### FR-11 惠民约束决策（创新点 1）
- 描述：预算分配不得因追求毛利而砍断民生商品；形式化为 R³ 多目标（收益–韧性–责任）整数优化。
- 验收标准：
  1. 民生商品先锁定最低覆盖（`LIVELIHOOD_MIN_COVER_DAYS=3` 天）不参与利润竞价；
  2. 预算极紧时按"客流带动系数 × 缺口"保底；
  3. MILP 不可用/超时自动回退贪心，系统不崩；
  4. 与纯利润基线对比时，民生保障率必须可量化更优。
- 状态：**已完成**（`policy.py` 三层分配 + `r3_optimizer.py` 两阶段字典序 MILP）

### FR-12 策略自进化（创新点 2）
- 描述：依据真实经营反馈校准安全系数与备货天数，形成"方案 → 反馈 → 校准 → 记忆"闭环。
- 验收标准：
  1. 触发阈值 `0.10`（小波动不触发）；步长/边界受硬约束（`0.05~0.60`、`2~12` 天）；
  2. 同日断货与损耗同现时只按断货处理（防止自我抵消）；
  3. 重复反馈幂等去重，不产生重复学习；
  4. 参数变化可在"它学会了什么"页面逐条追溯。
- 状态：**已完成**（`core/evolution.py`，11 项测试）

### FR-13 事件感知与证据门控
- 描述：识别高温/暴雨/节假日/供应商断供；事件对需求的影响必须先通过历史证据检验。
- 验收标准：
  1. 影响倍数从本店历史现算（同星期几基线，夹紧 `[0.5, 1.8]`），不是写死；
  2. 证据分级 strong/weak/insufficient，只有 strong 才改预测；
  3. 断供走供给侧逻辑（停采该供应商 + 环境强制拦截），不混入需求 uplift。
- 状态：**已完成**（`events.py` + `event_evidence.py`，12 项测试）

### FR-14 评测与实验能力
- 描述：提供可复现的对照实验：离线 60 天多决策方式重演，180 天长期仿真（含消融与压力测试）。
- 验收标准：同一预算/需求/事件下公平对比，差异可归因到单一设计点；结果落盘 CSV/JSON 并可被页面读取。
- 状态：**已完成**（`eval.py` / `core/eval_core.py` / `run_digital_store.py` / `run_event_awareness_ab.py`；FINAL 已冻结于 2026-10-02）

## 6. 指标定义与成功标准

### 6.1 指标口径（唯一定义在 `core/metrics.py`）

| 指标 | 定义 | 越大越好? |
|---|---|---|
| 断货率 | 缺货量 / 需求量 | 否 |
| 服务水平（满足率） | 实际售出 / 需求量 | 是 |
| **民生保障率** | 达到最低保障要求的民生商品数 / 民生商品总数 | 是 |
| **民生断货量** | 民生商品的缺货件数（惠民约束的核心观测） | 否 |
| 损耗率 | 报损件数 / 售出件数 | 否 |
| 损耗成本 | 报损件数 × 进价 | 否 |
| 毛利 | 售出 × 单位毛利 − 损耗成本 | 是 |
| 平均库存资金占用 | 日终库存价值均值 | 否（越低越轻） |
| 库存周转 | 销货成本 / 平均库存资金 | 是 |

### 6.2 成功标准（项目级）

| # | 标准 | 判定方式 | 现状（FINAL 冻结数据，budget ¥1800 / seed 42 / 180 天） |
|---|---|---|---|
| S1 | 民生保障率不低于纯利润基线，且民生断货量显著更低 | 主对比实验 | ✅ 1.000 vs 0.948；民生断货 425 vs 681（−37.6%） |
| S2 | 毛利不因惠民约束显著受损 | 主对比实验 | ✅ ¥152,707 vs ¥152,770（−0.04%，以极小代价换取民生保障） |
| S3 | 经营记忆带来可量化增益 | Memory A/B | ✅ 毛利 ¥152,707 vs ¥151,955（+¥752）；断货率 2.93% vs 3.40%；民生断货 425 vs 498 |
| S4 | 决策全程可解释、可追问 | 页面 + 六工具追踪 | ✅ 已完成 |
| S5 | 无网络/无 Key 环境功能不降级 | 去掉 `DEEPSEEK_API_KEY` 启动 | ✅ LLM 降级为规则模板 |
| S6 | 结果可复现 | 固定 seed + 固定 CSV | ✅ 已冻结（`eval/final/FROZEN.json`） |

## 8. 数据与假设边界（必须如实对外表述）

1. **仿真数据，不是真实门店采集数据**：`data/shopmind_products_50sku.csv`（50 SKU）+ `data/shopmind_180days_50sku.csv`（180 天 × 50 SKU = 9000 条，2026-03-01 ~ 2026-08-27，19 个民生商品）。
2. **CSV 只记录实际销量**，`qty_stockout` 与 `qty_spoilage` 全为 0；店主历史上的"想买没买到/卖不掉"**未被采集**，因此"店主原做法"的断货/报损恒为 0 属于数据局限，不能解读为店主做得更好。
3. **品类影响倍数由 CSV 现算**，不是外部喂给的答案；Agent 看到的世界 = 店主看到的世界。
4. **三档预算不可混用**：网页 ¥600（日常偏宽裕）、离线评测 ¥360（故意设紧，让"预算一紧先砍民生"显形）、长期仿真 ¥1800（普通日够周转、峰值日偏紧）。
5. **可推广性**：决策逻辑与 SKU 数量无关，瓶颈在数据积累；冷启动用最小可用假设兜底，跑满 2~4 周可学到本店规律。

## 9. 术语表

| 术语 | 含义 |
|---|---|
| 小满 / 店脑 | 同一系统的产品名 / 工程名 |
| 惠民约束（Responsibility） | 保障民生商品最低覆盖、不被利润竞价挤掉的决策约束 |
| 民生商品 | CSV 中 `essential=1` 的商品（本项目 19 个） |
| 潜在需求 | 实际销量 + 未满足缺货量（断货日的真实需求还原） |
| 目标覆盖天数 | 供应商交期 + 补货缓冲 + 民生保障缓冲，并受保质期上限约束 |
| 安全库存 | 预测需求 × 覆盖天数 × 安全系数 |
| 经营经验 | 反馈超阈值后沉淀的可复用教训（experiences 表） |
| 策略校准 | 经验 → 安全系数/备货天数的小幅有界调整 |

| 便民指数 / 民生保障率 | 民生商品达到最低保障要求的比例 |
